# 05 · GitHub Actions 编译

workflow：`.github/workflows/embedai.yml`，两个 job。

## validate（快速门禁）

每次 push / PR 都跑：

1. 缓存上游层仓库（按 `kas.yml` 的 repo 段 hash 做 key）
2. `kas dump` 展开配置
3. `kas shell kas.yml -c "bitbake -p"` 解析全部 layer/recipe

约 1–3 分钟。**注意**：bitbake 的 HOSTTOOLS 校验需要 `chrpath diffstat`，job 里必须 `apt-get install`，否则解析直接报错。

## build（完整编译）

- `runs-on: ubuntu-22.04`，public 仓库 → **4 核 / 16GB / 14GB SSD**
- `timeout-minutes: 350`（GitHub 托管 runner 硬上限是 **6 小时**，设更大也会被夹到 360）
- `concurrency`：同分支新 run 取消旧 run，避免重复重型编译

关键步骤与原因：

| 步骤 | 作用 |
|------|------|
| `jlumbroso/free-disk-space` | 删掉镜像预装软件，把可用磁盘从 ~14GB 提到 **~50GB** |
| `Generate CI kas config` | 把 `kas.yml` 里本机硬编码的 `DL_DIR` / `SSTATE_MIRRORS` 中和成工作区路径（见 [06](06-gotchas.md)） |
| 5h 预算 + SIGINT | 到点向 bitbake **进程组**发 SIGINT 优雅收尾（kas 用 asyncio 子进程，普通 `timeout` 杀不到 bitbake） |
| Save sstate | 滚动 key `embedai-sstate-<run_id>`，`restore-keys: embedai-sstate-` 前缀取最新 |
| Upload artifact | 产物 `build/tmp/deploy/images/jetson-orin-nano-devkit-nvme/embedai-image-*` |

## 为什么要“分次续跑”

完整 Jetson 编译在 4 核 runner 上**超过 6 小时**，必然被平台强杀。因此：

- 内部 5h 主动停 → 保存 sstate 缓存 → 下次 run 恢复后从断点继续
- 首次无缓存时可能要 2–3 轮才能编完；之后有缓存则增量、很快
- sstate 约 4.7GB（<10GB 缓存上限），上游层缓存约 0.4GB
- **下载目录（`DL_DIR`）约 21GB，超出缓存上限，不缓存**，恢复运行时只重新下载“尚未完成任务”所需的源码

## 已踩过的 CI 坑

1. **HOSTTOOLS 缺 `chrpath diffstat`** → validate 解析失败（已修）。
2. **480 分钟无效**：托管 runner 上限 6h，被夹到 360（已改 350 + 内部 5h 预算）。
3. **重复 run 并行**：加了 `concurrency` 组（旧 run 若定义里没有 concurrency，不会被自动取消，需手动 `gh run cancel`）。
